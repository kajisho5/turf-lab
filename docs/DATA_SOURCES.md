## 1. keiba.go.jp 公式データ（最優先のデータ源）

netkeiba スクレイピング（WAF障害・パース失敗・門別偏り）の代替。UTF-8・CSV・全13場。

### エンドポイント（直リンクでZIP取得可）
```
レース: https://www.keiba.go.jp/KeibaWeb/DataDownload/RaceDataDownload?type=monthly&k_year=YYYY&k_month=M
オッズ: https://www.keiba.go.jp/KeibaWeb/DataDownload/OddsDataDownload?type=monthly&k_year=YYYY&k_month=M
当日  : 上記の type=daily（約2分ごと更新）
```
マニュアル: https://www.keiba.go.jp/pdf/manual/data_pdf_manual.pdf

### 提供範囲（重要な制約）
| データ | 範囲 |
|---|---|
| レース情報・払戻 | **1998年〜**（全期間） |
| オッズ | **2026年3月〜のみ** ← それ以前は空(116バイト)。過去のオッズは取得不能 |

**オッズが2026年3月からしか無いことが、過去の買い方検証における最大の制約。**
人気(pop)は horselist に全期間入っているので、市場確率の代用にはそちらを使う。

### 取得方法
```
python backtest/fetch_nar.py 201501 202607        # Windows対応（urllib+zipfile）
python backtest/nar_data_pipeline.py 202401 202607 # Linux用（curl/unzipに依存）
```
`nar_data_pipeline.py` は curl と unzip の外部コマンドを呼ぶので **Windowsでは動かない**。
Windows では `fetch_nar.py` を使う（ZIPは解凍せず保存し、解析側が zipfile で直接読む）。

### コーナー通過順の書式
```
(1,10),9,6,(3,4),7,(2,5,8)
```
- 先頭から順に前。**括弧内は同じ位置**（横並び）
- 区切りは `,` と `-`（`-` は差が開いていることを示すが、順序の意味は同じ）
- **最終コーナー = 非空の最後の列**（地方は2コーナーしか記録が無いレースも多い）
- 位置 ÷ 頭数 = **実測先行力の元データ(pf)**。括弧内は平均順位を割り当てる

通過順の取得率は 2005年以降で80%前後。**1998-2000年は37-48%と低く、集計のノイズ源になる**。

### ハロンタイム（35-49列）の注意 — 2026-08-04に検証して不採用
- **収録は南関4場（大井/川崎/浦和/船橋）＋園田のみ**。他場は全欠損で、
  欠損は「場」で決まる。全期間で安定して21-22%（44,079R / 202,599R）。
  **全場を混ぜて集計すると場の差を因子の効果と誤認する**ので、収録場だけを分母にすること。
- **ラップ合計 = 勝ちタイム（完全一致を実データで確認）**。したがって平均ラップは
  既存の「レースレベル（標準タイム−勝ちタイム）」と同一情報で、足す意味は無い。
- 新情報は前傾度（前半3F−後半3F）だけ。1-3人気で-2.1〜-2.6ptだが4人気以下はゼロ。
  詳細と却下理由は docs/FACTS.md §3 と backtest/research_log.md。
- 索引: `backtest/nardata/lap_index.json`（`build_lap_index.py` で再生成）。
  南関限定の分析・記事には使える。

## 4. netkeiba（当日の予想取得で使用）

- 出馬表・結果・一覧は**全てUTF-8**。過去に EUC-JP と誤認して文字化けし、ファイナル判定に失敗した
- 取得経路: `/odds/proxy.php?u=` + base64url(URL)
- **絶対パスで叩く。** 相対パスだとルート表示のブラウザで404になる（v356の事故）
- 出馬表fetchは既にgzipが効いている（伸びしろ無し）。馬キャリア(db.netkeiba)は
  サーバーが Accept-Encoding を無視して非圧縮で返すため、こちらからは改善不可
- 並列度: 出馬表は3並列で4.9倍速・全HTTP200。馬キャリアは8並列まで確認済み
- `entries` は**配列ではなく馬番をキーにしたオブジェクト**。`Object.keys(entries)` で回す

### parseShutuba の返り値
```js
{ entries: {"1": {num, name, waku, jockey, past:[...], ...}, ...},
  order: ["1","2",...],
  cond: {surface, dist, going, weather, raceName, turn} }
```
`past[]` の1件: `{rank, dist, going, time, passing:"10-9-9-9", style:"追", pop, fieldN, rdate, rid, track, ...}`

## 5. JRA-VAN Data Lab（JV-Link）— 中央競馬

2026-07-19 に接続確認済み。**地方(keiba.go.jp)には無い「全券種の確定オッズ」が取れる。**

### 環境の落とし穴（3つとも実際に踏んだ）
1. **JV-Link は 32bit COM**（`C:\Windows\SysWOW64\JVDTLAB\JVDTLab.dll`）。
   64bit の Python / PowerShell からは「クラスが登録されていません」で失敗する。
   → **32bit PowerShell** から使う。追加インストールは不要:
   `C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`
2. **JVRead/JVGets を PowerShell から直接呼ぶと SEHException で落ちる**（BSTR参照渡しのマーシャリング）。
   → C# の `ParameterModifier` 経由で呼ぶ。さらに**バッファを事前確保**して渡す
   （`new string(' ', 120000)`。空文字だと invocation 例外）。
3. **.ps1 は UTF-8 BOM付きで保存する。** PowerShell 5.1 は BOM無しを Shift-JIS として読むため
   日本語コメントが壊れて構文エラーになる。

### スクリプト
| ファイル | 用途 |
|---|---|
| `backtest/jvlink_dump.ps1` | 蓄積系(JVOpen)を1行1レコードで書き出す |
| `backtest/jvlink_rt.ps1` | 速報系(JVRTOpen)。オッズ取得はこちら |
| `backtest/jvlink_probe.ps1` | DataSpec の有効性確認 |

### DataSpec（実測）
- **有効**: RACE / TOKU / DIFF / BLOD / MING / SNAP / SLOP / WOOD / YSCH / HOSE / HOYU / COMM
- **無効(rc=-111)**: O1 / O2 / ODDS / 0B30 …
  → **蓄積系にオッズは無い。オッズは速報系(JVRTOpen)のみ。**
- rc=-1 は「該当データ無し」、-111 が「DataSpec不正」。区別すること

### レコード
- 固定長・Shift-JIS。先頭2文字が種別ID（RA=レース詳細1131字 / SE=馬毎レース情報377字 / HR=払戻 …）
- 共通ヘッダ: 種別(2) 区分(1) 作成年月日(8) 開催年(4) 月日(4) 場(2) 回次(2) 日次(2) R(2)
- オッズ(O1〜O6)は続けて **発表月日時分(8) 登録頭数(2) 出走頭数(2)**
  - O1=単複枠 / O2=馬連 / O3=ワイド / O4=馬単 / O5=3連複 / O6=3連単
  - `JVRTOpen("0B30", レースキー)` で**6種すべて**返る
  - レースキー16桁 = YYYYMMDD + 場(2) + 回次(2) + 日次(2) + R(2)

### オッズ時系列について（重要）
確定後に取れるのは **データ区分=4（確定）の1スナップショットだけ**。
**過去に遡って時系列は取得できない。** 欲しければ当日に定期実行して自分で貯めるしかない。
これは地方(keiba.go.jp)と同じ制約。

ただし**過去の払戻は蓄積系の HR レコードで取れる**ので、回収率のバックテストは全期間可能。

### JV-Link 蓄積系の正しい取り方（2026-07-19 実測で判明・重要な訂正）

**① セットアップモード(option=4)は使わない。**
全期間で投げたら3時間戻ってこず、5.8MBしか落ちなかった。プロセス停止で解決。

**② option=1（通常データ）が FromTime を尊重して過去まで遡る。**
```
FromTime=20260701 →    56ファイル
FromTime=20260101 →   733ファイル
FromTime=20250101 → 1,370ファイル ← 上限
FromTime=20240101 → 1,370ファイル（2025と完全同一・ハッシュ一致）
```
**1,370ファイルが上限＝実質1年分**。それ以前は option=1 では取れない。
（当初「2年分」と書いたが誤り。中身の開催日を見ると **2025-07-19 〜 2026-07-19 の112開催日・3,565レース**しかない。
ファイル数の上限であって期間の上限ではないので、必ず中身の日付範囲を確認すること。）
全JVOpenが100-200msで即答するので、年単位ループが現実的。

**③ 「蓄積系にオッズは無い」は誤りだった。**
`JVOpen("O1",...)` が rc=-111 になるのは**指定方法が不正**なだけ。
`RACE` を指定すればオッズも払戻も一緒に降ってくる:
```
RA=3,565(レース) SE=49,218(馬毎) HR=3,450(払戻)
O1〜O6=各3,480(単複枠/馬連/ワイド/馬単/3連複/3連単)
H1/H6=3,450(票数) WF=81 JG=53,239
```
→ **JRAは過去のオッズが取れる。**地方（公式は2026年3月以降のみ）に対する大きな優位。

**④ 取得スクリプト**: `backtest/jvlink_fetch_all.ps1`（年単位ループ・既取得はスキップ）
出力は `backtest/jvdata/race_YYYY.txt`（gitignore）。2025年分で約400MB。

### JV-Data レコードのフィールド位置（実データから同定・2026-07-19）

**仕様書の記憶で書くとずれる。ずれても数値は読めてしまうので気づけない。**
以下は `probe_se_layout.py` / `probe_hr_layout.py` で制約を使って同定し、
`parse_jvdata.py --verify` で全3,450レース照合済みの値。**0基点のバイト位置**。

**SE（馬毎レース情報・553バイト）**

| 項目 | 位置 | 同定に使った制約 |
|---|---|---|
| レースキー(年月日場回日R) | 11:27 | — |
| 馬番 | 28:30 | — |
| 確定着順 | 334:336 | レース内で1..Nの順列 |
| 単勝オッズ(×10) | 359:363 | 人気順に単調増加 |
| 単勝人気 | 363:365 | レース内で1..Nの順列 |
| コーナー通過順 1c/2c/3c/4c | 351/353/355/357 | 各2バイト |

※ 入線着順(332:334)と確定着順(334:336)は隣接し、通常は同値。混同しないこと。

**HR（払戻・717バイト）** — `(先頭, 件数, 組の桁, 1件のバイト数)`

| 券種 | 先頭 | 件数 | 組 | 1件 | 終端 |
|---|---|---|---|---|---|
| 単勝 | 102 | 3 | 2 | 13 | 141 |
| 複勝 | 141 | 5 | 2 | 13 | 206 |
| 枠連 | 206 | 3 | 2 | 13 | 245 |
| 馬連 | 245 | 3 | 4 | 16 | 293 |
| ワイド | 293 | **10** | 4 | 16 | 453 |
| 馬単 | 453 | 6 | 4 | 16 | 549 |
| 3連複 | 549 | 3 | 6 | 18 | 603 |
| 3連単 | 603 | 6 | 6 | **19** | 717 |

払戻額はどれも9桁。人気欄は残り（3連単だけ4桁）。

**★踏んだ罠3つ★**
1. **ワイドは7枠ではなく10枠。** 7だと以降の券種が全部ずれる。
2. **3連単だけ1件19バイト。** 組合せが最大4,896通りで人気欄に4桁必要なため。
   18で読むと2件目以降が1バイトずつずれ、1億円級の払戻が混入して
   全通り買いROIが**1580%**になった。`603 + 6×19 = 717` がレコード長と一致するのが正解の目印。
3. **SEは (レース, 馬番) で一意化する。** option=1 は FromTime 以降を丸ごと返すので
   年をまたいで取るとファイル間で期間が重なる。素朴に append すると同じ馬が2回入り、
   着順リストが壊れる（2026年分だけ検証が全滅した）。

**検証の作り方（重要）**
`--verify` は「馬連の組＝着順上位2頭」「3連単の組＝上位3頭の順序通り」を照合する。
ただし**1件目だけ見ていると2件目以降のずれを見逃す**（罠2はこれで一度すり抜けた）。
全行について「組が出走馬番の重複なしの並び」であることまで見ること。

# 中央競馬（JRA-VAN / JV-Data）

## 取得元は TARGET frontier のローカルファイル

**JV-Link で落とし直す必要は無い。** `JVOpen(option=4)` は指定年から現在までを
毎回まるごと落とし直すので極端に遅く、8時間かけて3年分しか取れなかった。

TARGET が `C:\TFJV\SE_DATA` に **1954〜2026年ぶん・5.7GB** を持っており、
中身は独自形式ではなく**生の JV-Data**。

| ファイル | 種別 | レコード長 |
|---|---|---|
| `SR*.DAT` | RA（レース詳細） | 1272B |
| `SU*.DAT` | SE（馬毎レース情報） | 555B |
| `SH*.DAT` | HR（払戻） | 719B |

各レコードは CRLF 終端なので、**連結するだけで JV-Link のダンプと同じ形式**になる。
`backtest/target_to_dump.py` が変換し、`parse_jvdata.py` がそのまま読める。

先頭2バイトが空白のレコードは TARGET の空きスロット（パディング）。**欠損ではない。**

## ★列位置は必ずバイトで数える★

最初 cp932 に decode してから**文字位置**で探して全部ずれた。
馬名などの漢字以降が丸ごと狂う。既存パーサーは**バイト位置**で読んでいる。
（1レコード 555バイト = 379文字）

### 特に価値が高い未使用データ

**1. CK_DATA（調教）602MB**
坂路とウッドチップの調教タイム。GBMの特徴量一覧に「調教」は**入っていない**ので、
まったく新しい因子になりうる。ただし例によって人気で統制すると消える可能性があるため、
採用前に必ず実測する。

**2. TM_DATA（JRA-VAN公式のマイニング予想）**
他社の予想と自分の予想を同じ物差しで比べられる。「AIどうしの比較」記事が書ける。
市場（人気）以外の比較対象を初めて持てる。

**3. BS_DATA（セリ価格）**
「高く買われた馬は本当に走るのか」を実測できる。記事として強い。

**4. HY_DATA（票数）1,958MB**
オッズがどう形成されたか。人気薄が割高になる仕組みを直接見られる。
